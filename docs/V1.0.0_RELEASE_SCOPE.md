# ALVM Studio 1.0.0 release scope

**Release policy:** The next planned public release after the current 0.9.6 development line is **1.0.0**. Do not create a 0.10.x release for this plan. Version 1.0.0 is a target, not a claim that the features below are already complete.

This document records the requested 1.0.0 scope and the actual baseline visible in the repository. A feature is complete only after its native implementation, compiler/runtime integration, tests and documentation are present. A UI card, snippet or browser-only preview does not count as an implementation.

## Release requirements and baseline

| Required area | Baseline in the repository | 1.0.0 completion gate |
|---|---|---|
| **ALVM Runtime: real .room bytecode execution** | **Implemented foundation.** The C++ compiler emits binary .room v10; the Rust CI Runtime validates and executes bytecode. Android calls the Rust runtime through JNI. | Verify the .room header, version, metadata, references, jumps and operand-stack states before execution. Keep source parsing/execution out of the VM. Add malformed-bytecode, invalid-control-flow, runtime-failure and C++/Rust parity tests. |
| **Programming: variables, functions, arrays and OOP** | **Partially implemented.** Scalar values, functions, primitive arrays, classes, fields, constructors, inheritance and overloads exist. | Complete the agreed language surface: robust function/recursion tests, array bounds and mutation tests, object arrays where supported, virtual dispatch, interfaces/abstract classes and access checks. Do not advertise unsupported generics or OOP behavior as complete. |
| **Graphics: colors, text, shapes and sprites** | **Partially implemented.** Native text/UI, basic 2D shapes and a new `UI.sprite` renderer backed by APK assets exist. Importing/packaging arbitrary user assets and full asset lifecycle management remain incomplete. | Implement color handling consistently in compiler, bytecode/runtime and Android renderer. Add text, rectangle, circle, image/sprite, transform, clipping and asset-failure tests on the native path. |
| **Game Engine: 2D, physics, collision and input** | **Partially implemented.** A 2D view, touch areas, frame callbacks, AABB overlap checks and a vertical gravity integrator (`UI.setVelocityY` / `UI.physicsStep`) exist. A full rigid-body physics solver and collision response are not present. | Add deterministic update timing, touch and supported keyboard/controller input, collision response, gravity, velocity and physics lifecycle. Add automated game-state tests and Android input/frame-timing smoke tests. |
| **3D Foundation: camera, objects and rendering** | **Planned; no complete native 3D pipeline is established.** | Define and implement a real renderer, camera/projection, 3D transforms, mesh/object lifecycle, depth handling and lighting. Add device capability/failure handling and rendering tests. Do not count a static preview as 3D support. |
| **Audio: sound effects and music playback** | **Planned; AL.Audio is not yet an executable native runtime API.** | Implement asset loading, play/pause/resume/stop, volume, completion/error callbacks and Android lifecycle cleanup. Add tests for missing assets, interruption and resource release. |
| **File System: .al, .room and .AL support** | **Partially implemented.** Workspace management supports .al and .room files; ALPK v1 .AL packages support one entry module and optional assets. The language-level AL.Files sandbox API and multi-module linking remain incomplete. | Verify create/open/save/rename/delete for .al and .room; create/verify/extract .AL packages safely; add path traversal, duplicate entry, size-limit and invalid-bytecode tests. Implement AL.Files only with app-sandbox and explicit capability checks. |
| **Debugger: runtime errors and debugging** | **Partially implemented.** Compiler/runtime errors are reported, but a full source-level debugger is not established. | Provide source-aware diagnostics and stack traces, stable source locations, breakpoints, step/continue, variable inspection and safe stop/reset behavior. Test nested calls, runtime faults and invalid source locations. |
| **Automated testing: all core features** | **Partially implemented.** C++/Rust end-to-end tests, negative fixtures and Android APK-builder tests exist. The full 1.0.0 matrix is not complete. | Add positive and negative automated tests for every release requirement, C++ compiler/VM versus Rust CI Runtime parity tests, Android host lifecycle/input/audio/rendering smoke tests and a passing CI release matrix. |

## Engineering order

1. **Lock the language and bytecode contract.** Keep the C++ compiler, binary .room format, verifier and Rust CI Runtime in sync. Any opcode or type metadata change requires a documented format-version decision and compatibility tests.
2. **Finish programming-language correctness.** Close the gaps in arrays, functions, OOP and diagnostics before layering more native APIs on top.
3. **Finish the 2D native graphics/game path.** Colors, text, shapes, sprites/assets, input, frame timing and physics/collision must run from compiled AL code.
4. **Finish file/package safety and debugger support.** Keep .al, .room and .AL distinct and validate all data before execution or extraction.
5. **Add audio and the 3D foundation.** These must be real platform/runtime implementations, not catalogue entries or mock previews.
6. **Run the complete release test matrix.** Preserve existing Studio features and verify Android behavior on a real emulator/device before calling 1.0.0 stable.

## Stable release gates

- No fake buttons, placeholder APIs or catalogue-only features.
- No feature marked complete without native implementation and automated tests.
- C++ compiler/desktop VM and Rust CI Runtime must agree on valid and invalid programs.
- Android rendering, input, audio and lifecycle behavior must be tested through the actual host.
- The VM executes verified .room bytecode only; it never runs .al source directly.
- Existing editor, project/file manager, Library Store, Website Builder, Chess UI and Android export flows must not regress.
- Build/version metadata must report the real app version and runtime version separately.
- Publish 1.0.0 only when every mandatory release gate above passes. Until then, keep it marked **in development**.
